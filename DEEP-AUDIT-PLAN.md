### E1 · `persist-cap-mismatch` — client accepts annotations the server silently discards → whole submission nulled on Save
*Merged: `persist-cap-mismatch-total-loss` + `resilience-oversize-blob-blocks-grade-and-erases-drawing`. Corroborated by pl-integration and exam-resilience areas.*
- **Severity:** Critical · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** medium
- **Location:** `prairielearn/example-course/elements/pl-scribble/pl-scribble.py:36-39,61,374-392` (MAX_JSON_NODES=500k / MAX_ANNOTATION_BYTES=16 MiB → `parse()` sets answer to `None` + `format_error`); client caps far looser: `scribble/src/model.rs:7-8,15` (5000 items/page, 30 MB); no guard in `scribble/web/app.js:1797-1808` (`serializeAnnotations`) or Rust `save_json` (`lib.rs:1153`).
- **Failure:** A heavy annotator crosses ~500k structural nodes (reachable at the client's *own* `MAX_ITEMS_PER_PAGE`=5000 with ~100-pt strokes — the **node axis**, not bytes; note reviewers corrected that clippings are stripped before submission so they don't count). The iframe shows all work; on Save/Save&Grade `parse()` raises, stores `None`, refuses to grade, and the panel re-seeds blank on reload. Every subsequent Save re-fails. No client warning ever appears; the error renders in PL chrome *outside* the iframe.
- **Fix:** (a) Client-side node/byte budget well under the server caps with a visible `aria-live` "Scratchpad is full — simplify to keep it savable" banner, and refuse to write an over-cap blob into the hidden input (keep last-good value so a Save can never be rejected). (b) Make `parse()` **degrade** — keep the last valid submission instead of overwriting with `None`. (c) The **node cap is the binding constraint** — raising `MAX_ANNOTATION_BYTES` alone is insufficient. Confirm PL's re-seed-on-format-error behavior on the deployed version (NEEDS LIVE for the "blank on reload" half).

### E2 · `core-id-realloc-duplicate-on-reload` — interleaved item creation makes a duplicate id → `validate()` discards the entire document on next load
- **Severity:** Critical · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** medium · **Effort:** small
- **Location:** `scribble/src/lib.rs:225,238` (Stroke/Shape take `id:self.next_id` at pointer-down **without** advancing it), `lib.rs:1293-1302` (commit advances only at commit), `lib.rs:378` (`add_text_on` advances immediately — asymmetric), `model.rs:441-443` (global `seen_ids` rejects any duplicate on load); JS gap `app.js:2818-2851` (SketchView pointer-down does not pre-commit an open text editor; the PDF path does at `app.js:1111`).
- **Failure:** On a Sketch note, type a text label then start inking **without pressing Enter**: the stroke and the blurred-textarea Text both take id N. `save_json` succeeds, but on the next load (autosave restore, or graded reopen/regrade) `validate()` returns `Err("duplicate item id")`, `load_json` throws, and the **whole annotation document is discarded** — shown only as a transient "Couldn't restore…" toast.
- **Fix:** Reserve the id at construction: add `fn alloc_id(&mut self)` and use it in `pointer_down_on` (Stroke+Shape) and `add_text_on`; **keep** the lazy `next_id = max(next_id, item.id()+1)` in `commit()` as a load-time floor. Belt-and-suspenders: have `SketchView.onPointerDown` commit any open editor first (mirror `app.js:1111`). Add a regression test interleaving `add_text` between down and up.

### E-SEED · `autosave-failure-is-invisible` — the save loop can fail silently and permanently, with no signal to the student and no telemetry to staff
*User-seeded and pre-confirmed (not surfaced by the audit — injected here). Ranked ABOVE the crash-window (E7) and final-window (E11) siblings per user direction: those lose a bounded ≤1.5 s; this can lose everything, forever, invisibly.*
- **Severity:** High (observability defect — certain; **Critical** if any deterministic trigger exists) · **exam_critical: yes** · **Verdict:** CONFIRMED (user-verified) · **Confidence:** high · **Effort:** small
- **Location:** `scribble/web/embed.js:22-42` (`wireSaveLoop`/`flush`), specifically the `catch { /* keep the dirty flag set; the next tick retries */ }` at `embed.js:32`; the flush triggers at `:34-41` (1.5 s interval + beforeunload/pagehide/visibilitychange/blur).
- **Failure:** `flush()` calls `serializeAnnotations()` and writes the blob to the hidden input. Its `catch {}` swallows **every** error with zero surfaced signal. If `serializeAnnotations` (or the input write) throws **deterministically** on some annotation/state, persistence fails silently and **permanently** — every 1.5 s tick re-throws and is re-swallowed. The student sees a normal-looking scratchpad that never actually saves; nothing warns them, and no log or telemetry reaches staff. The discriminating question — *does a persistence failure ever become visible to anyone?* — has the answer **no**, today, in any mode. (Distinct from E1, which at least emits a PL format-error, and from E2, where serialize succeeds but the next **load** fails.)
- **Fix:** Make persistence failure observable. On a `flush` throw: surface a persistent, `aria-live` in-frame "Couldn't save your work — tell a proctor" state to the student (not a 4 s toast); count consecutive failures and stop pretending success. Emit a staff-observable signal where one is reachable (a distinctive `console.error`, and — if a channel exists — a marker written into the hidden input or a PL-visible field so a failing save is detectable server-side). Do **not** leave the retry infinitely silent. Pair with E7 (durable local snapshot) so a detected failure has a fallback. *Note:* a `save_json` **panic** (not a JS throw) traps the whole WASM instance under `panic="abort"` — that path is even more catastrophic and is covered by the Rust-core panic-safety work (Batch R / E2 family); this item is specifically the JS-throw-swallowed-silently case.

### E-NOTES · `notes-non-durable-silent` — the first-class Notes surface is silently stripped on save, while the UI copy tells the student it's kept
*Promoted into §0 from the exam-resilience batch during SDM review: this is unconditional silent loss of graded-looking work, actively worsened by misleading copy — a stronger mid-exam data-trust trap than E8/E11.*
- **Severity:** Medium · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** small
- **Location:** `app.js:1799-1807` (`serializeAnnotations` sets `o.notes=[]` — notes are stripped from the saved blob; hydrate never restores them); the dirty flag is cleared by adding a note (no unsaved warning); **misleading copy** at `app.js:2629` ("Scratch work is included when you click Save."), `:2635` ("…snip a region into your answer's notes **to keep it**"), `embed.js:143-144`.
- **Failure:** Notes is a prominent `+Text / +Draw / +Paste` surface (it's also the **paste target** the whole reference-tool workflow feeds into). A student works a derivation into a note, sees copy saying it's saved, clicks PL Save (whose unsaved-warning fires on the already-stripped blob — false reassurance), and the note is silently gone from the submission. They believe graded-looking work is stored when it never was.
- **Fix:** Either **persist notes** (they're size-capped, so this is viable) — or, if they must stay scratch: a standing "Notes are scratch — NOT saved with your answer" label, a confirm before discarding non-empty notes, **and correct/remove the "included when you Save" / "to keep it" messages** so the copy stops promising durability the code doesn't deliver.

### E3 · `overlay-annotate-eats-widget-clicks` — in Annotate mode the transparent overlay captures clicks meant for nested graded widgets → student's real answer never registers
*Merged: `overlay-annotate-eats-graded-widget-clicks` (gap-exam-integrity) + `overlay-draw-mode-blocks-answering-no-feedback` (gap-real-student).*
- **Severity:** High (Critical if overlay wraps a graded widget) · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** medium
- **Location:** `pl-scribble.py:134` (`f.style.pointerEvents = on?'auto':'none'` — whole iframe), `:351` (`_OVERLAY_WRAP` nests widgets under the frame), stale/contradictory comments `:240-243,347-351` ("nested inputs stay answerable … verified end-to-end"); default tool = pen `index.html:109`.
- **Failure:** A question wrapped in `<pl-scribble mode="overlay">` with an inner `pl-multiple-choice`/`pl-*-input`: student clicks Annotate, then — without pressing Done — clicks radio (B); the click lands as a pen dot, the radio stays unselected, and on Save the graded field is blank → zero credit for a question they believe they answered. ### E4 · `ref-locked-strand-on-cap` — a locked reference that trips a size/page cap strands the student with a blank, un-openable tool for the rest of the exam
- **Severity:** High · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** small
- **Location:** `app.js:2310-2331` (`openReferenceFile` adds `body.locked` before load), `:2323` (`routeOpen` not awaited), `:685-688,697-701` (`openPdf` caps `status()` + `return`, never throws), `style.css:1516-1520` (`.locked` hides `#btn-open`), `:224` (status auto-clears at 4s).

If `!ok`, remove `body.locked` and show a persistent message. Independently, raise/drop the caps for trusted same-origin instructor references (caps exist to guard hostile *uploads*, not instructor-shipped files).

### E5 · `core-note-block-delete-irreversible` — one-click, no-confirm, no-undo deletion of a whole Sketch note
- **Severity:** High · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** small
- **Location:** `scribble/src/lib.rs:1038-1049` (`remove_note`), `:817-821` (notes deliberately bypass undo), `:1067-1069` (clears sketch-referencing undo history); trigger `app.js:2721` (`✕ Delete block` → `app.remove_note(i)`, no confirm; the `↑ ↓ ✕` controls sit adjacent at `:2719-2721`).

### E7 · `crash-recovery-embed` — no durable autosave in exam modes; unsaved work lives only in an in-DOM input until the student manually clicks PL Save
*Merged: `resilience-no-crash-recovery-in-embed` (rated critical) + `persist-no-crash-recovery-embed` (rated high, adjusted to medium). The two areas corroborate the mechanism but split on severity; landing at **High**.*

### E10 · `resilience-schema-drift` — a mid-exam redeploy that changes the blob schema orphans in-flight work, then the save loop overwrites it
- **Severity:** Medium (reviewer: PL retains full submission history, so prior work is instructor-recoverable — harm is a blanked live state, not irrecoverable loss) · **exam_critical: yes** · **Verdict:** CONFIRMED · **Confidence:** high · **Effort:** medium
- **Location:** `scribble/src/model.rs:261,352-353` (Document carries `version:u32`, strictly enforced — so the finding's "no version field" premise is **wrong**; the risk is *sharper*: bumping `DOC_VERSION` hard-rejects all prior blobs), `app.js:1813-1852` (`hydrateAnnotations`), `embed.js:22-34` (flush runs unconditionally after a failed hydrate).
- **Failure:** Professor pushes a schema-changing hotfix mid-exam (the deploy flow allows it). A student reloads → `load_json` rejects the old blob → "starting fresh" toast (missed over the transparent overlay) → one stroke → auto-flush overwrites the good submission. Rollback no longer recovers the live state.
- **Fix:** After `hydrateAnnotations` returns false for a **non-empty** seed, **latch autosave off** (refuse to overwrite `input.value`) until the student explicitly discards. Make version handling migrating/tolerant rather than reject-only. Operational rule: never deploy a schema-changing bundle while an exam is open.

### E11 · Save-boundary loss windows — the app suppresses its own unsaved guard and the last ≤1.5 s of work can miss a non-navigation submit
